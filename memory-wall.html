Compute raced ahead. Memory didn't.

Ever wondered why this problem keeps getting worse, not better? Each new GPU generation adds far more maths than memory bandwidth. Since 2016, NVIDIA's data-centre chips have gained about 100× in FP16 compute but only about 11× in bandwidth. The shaded gap between the two lines is the memory wall.

Prefill vs. decode, with the real arithmetic

Llama 3 70B in FP16 on one H100. Weights: 70.6 billion parameters × 2 bytes ≈ 141 GB. Every weight is used for one multiply and one add per token, so 2 FLOPs per parameter per token.

Part 4 · Real models

Today's open models, side by side

KV per token = 2 (K and V) × layers × KV heads × head size × 2 bytes. "Max decode" is H100 bandwidth ÷ weight bytes at batch 1: a hard ceiling, not a benchmark.

Models bigger than 80 GB don't fit on one H100, so they're split across several, which adds bandwidth but also communication cost. DeepSeek-V3 is a mixture-of-experts model: only about 37B of its 671B parameters are used per token, and its compressed attention (MLA) shrinks the cache further. GPT-4, Claude and Gemini don't publish their architectures, so they can't be listed.

Part 5 · Questions

The questions that make it click

The points that usually stay fuzzy after seeing the formula. Tap one to open it.

Is arithmetic intensity a property of the chip or of the workload?

Of the workload. Every operation does some amount of work per byte it moves: an elementwise add on FP32 numbers does about 0.08, decode at batch 1 does about 1, a big matrix multiply does over 1,000. The chip has its own ratio, peak FLOP/s ÷ bandwidth, called the ridge point. Compare the two and you know which wall you'll hit. Stages 2 and 3.

If the intensity is 64 and the bandwidth is 64 GB/s, is the throughput 64 × 64?

Yes: 4,096 GFLOP/s, as long as that's below the chip's peak. Achievable throughput is always min(intensity × bandwidth, peak). That one line is the whole roofline model. Stage 4.

Does the KV cache count only the prompt, or the output too?

Both. It holds every token in the context: the prompt plus everything generated so far. Each new output token adds its own key and value in every layer, so the cache keeps growing until the sequence ends. A "100k-token context" means 100k in total. Stage 8.

Why are output tokens usually priced higher than input tokens?

A big part of it is this page. Input tokens go through prefill, where thousands of tokens share one read of the weights, so the GPU runs near full speed. Output tokens come out one at a time, each paying for a full read of the weights and the cache. Same chip, very different amounts of useful work per second. Part 2.

Why don't providers just batch thousands of users together?

They batch as much as they can, but each user brings their own KV cache, and it has to be read on every step too. Unlike the weights, it isn't shared. With long contexts the cache soon outweighs the model, intensity stops climbing, and memory capacity runs out. Bigger batches also make each user's tokens arrive more slowly. Stages 7 and 8.

Does quantisation make the model faster even if the maths is the same?

For decode, yes. Going from FP16 to INT4 cuts the bytes per weight by 4×, and since decode time is mostly bytes ÷ bandwidth, the speed ceiling rises by roughly 4×. The multiply-adds barely matter, because the cores were idle anyway. Try the precision menu in Part 3.

How does speculative decoding get around the wall?

A small, cheap model guesses the next few tokens. The big model then checks all of them in one pass, like a tiny prefill. The weights are read once but used for several tokens, so the intensity goes up. When the guesses are right you get several tokens for the price of one read.

Why are Groq and Cerebras so much faster?

They attack the bandwidth term directly. Instead of keeping weights in HBM next to the chip, they keep them in on-chip SRAM, which is far faster to read, and spread the model across many chips. More bytes per second means more tokens per second, which is how they reach 1,000+ tokens/s on some models.

So how does anyone make inference faster?

Every trick is one of three moves. Move fewer bytes: quantisation, grouped-query attention, compressed caches like MLA, mixture-of-experts. Do more work per byte: batching, speculative decoding, FlashAttention (which keeps data in fast on-chip memory). Get more bandwidth: HBM3e on H200 and B200, or SRAM-based chips. Prefill is a maths problem; decode is a memory problem, and most of the effort goes into the second.
